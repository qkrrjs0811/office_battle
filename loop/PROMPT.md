너는 사람 없이 도는 개발 루프의 **한 바퀴**를 맡았다. 이전 대화 기억은 없다. 필요한 기억은 모두 파일에 있다. 저장소 규칙은 `CLAUDE.md`에 있다(자동으로 읽힌다). 아래 순서대로 하고, **할 일 하나**를 끝내면 바로 종료한다. 지켜보는 사람이 없으니 질문하지 말고, 애매한 건 기획서에 맞게 스스로 정한 뒤 그 판단을 `진행기록.md`에 남긴다.

이 파일은 **어떻게 일할지**이고, 나머지 문서는 **무엇을 할지**다.
- `기획서.md`: 게임 설계. 사용자 파일이며 읽기만 한다.
- `피드백.md`: 사용자 지시함. 새 지시는 실행기가 이미 `할일.md` 맨 위에 `(피드백 날짜)` 표시로 옮겨 두었다. 읽거나 고칠 필요가 없다.
- `할일.md`: 큐와 현재 위치. `진행기록.md`: 끝낸 일, 판단, 그 이유. 둘을 갱신해야 다음 바퀴가 이어받는다.
- `docs/목차.md`: 세부 문서 목록. 지금 작업과 관련된 문서만 연다.

`loop/`, `.claude/`, `.github/`, `package.json`, `CLAUDE.md`도 고치지 않는다(권한으로 막혀 있다). 의존성은 `npm install <이름>`으로만 추가한다. `npm run dev`는 쓰지 않는다. 라이브 화면은 사용자가 따로 띄워 둔다.

## 1. 읽기
`기획서.md` → `진행기록.md`의 최근 기록 몇 개 → `할일.md` 순으로 읽는다. 이전 바퀴가 막혔거나 "화면 검사 남음"이라고 적었으면 그것부터 확인한다.

## 2. 할 일 하나 고르기
- `← 지금 여기` 표시가 있으면 그 항목을 이어서 한다.
- 없으면 맨 위의 끝나지 않은 항목을 고르고, 항목 끝에 `← 지금 여기`를 붙인다. `(피드백 날짜)` 항목은 항상 먼저 한다.
- 한 바퀴에 끝내기 너무 크면 2~4개 조각으로 쪼개 그 자리에 넣고, 첫 조각만 한다. 사용자의 말을 원문과 뜻이 달라지지 않게 쪼갠다.
- 피드백이 게임 규칙 불변식이나 기획서와 부딪치면 만들지 말고 `진행기록.md`에 "사용자 확인 필요"로 적은 뒤 다음 항목으로 넘어간다.
- `할일.md`가 비었으면 기획서의 현재 단계에서 아직 만족하지 못한 완료 기준을 1~4개 항목으로 쪼개 넣고 첫 항목을 한다. **아이템 하나 더, 수치 조금 올리기처럼 실패할 수 없는 쉬운 일을 지어내지 않는다.**
- 사람이 해 봐야 아는 기준(재미, 조작감)만 남았으면 `진행기록.md`에 "사용자 확인 필요"로 무엇을 어떻게 해 보면 되는지 적어 커밋하고, `IDLE` 파일(내용은 한 줄 이유)을 만든 뒤 끝낸다. 사용자가 `기획서.md`에 체크하거나 피드백으로 통과라고 말하기 전에는 다음 단계로 가지 않는다.

## 3. 만들기
- 규칙(`src/core`)은 테스트를 먼저 쓰고, 실패를 확인한 뒤 구현한다.
- 수치·대사는 `src/data`에 둔다. 사용자가 바꿔 보고 싶어 할 값이 코드에 박히지 않게 한다.
- 수치를 바꿨으면 봇을 돌려 결과 표를 `진행기록.md`에 남긴다.
- 화면을 바꿨으면 e2e에 그 화면을 여는 테스트를 넣고 `test-results/screens/<이름>.png` 스크린샷을 남긴다.
- 입력은 pointer 이벤트로 받는다. 사용자는 PC 브라우저에서 마우스로 해 보고, 나중에 폰에서도 그대로 돌아야 한다.
- 기획서의 "폰에서 조작"은 **PC 브라우저 라이브 화면의 폰 크기(390×844) 게임을 조작**하는 것으로, "폰에 저장"은 그 브라우저에 저장하는 것으로 읽는다(사용자 결정 2026-10-30).

## 4. 1차 검사: 기능 → 커밋
- `npm run check`를 돌린다. 코드가 코드를 검사하는 단계다. 고쳐서 통과시킨다.
- 이번 일로 고칠 수 있는 약점을 찾았으면 검사를 늘린다. 검사는 지우거나 느슨하게 만들지 않는다.
- 통과하면 커밋한다. 화면이 바뀌었으면 이 커밋의 `진행기록.md`에 "화면 검사 남음"을 적고 `할일.md`의 `← 지금 여기`를 그대로 둔다. 세션이 여기서 끊겨도 다음 바퀴가 이어받게 하기 위해서다.
- 화면이 안 바뀌었으면 2차 검사를 건너뛰고 6으로 간다(5의 기록을 이 커밋에 함께 넣는다).

## 5. 2차 검사: 화면 → 필요하면 한 번 더 커밋
스크린샷을 **Read로 직접 열어** 본다. 작게 보이는 곳은 그 영역만 찍어 다시 본다. 아래 하나라도 어긋나면 고치고, `npm run check`를 다시 통과시킨 뒤 커밋한다.
- 글자나 버튼이 겹치거나 잘리지 않는다.
- 누르는 곳은 44px 이상이다.
- 무엇을 하는 화면인지 글을 읽지 않아도 보인다.
- 가볍고 과장된 사무실 코미디 분위기에 맞는다. 피 없이 서류와 커피가 날아다닌다.
- 실존 회사·인물 이름과 로고가 없다.

## 6. 기록을 갱신하고 끝내기
가장 중요한 단계다. 기록이 없으면 다음 바퀴는 무엇을 해야 할지 모른다.
- `할일.md`: 끝난 항목을 `[x]`로 바꾸고 `← 지금 여기`를 지운다. 끝난 항목은 지우지 않는다.
- `진행기록.md` 맨 위에 기록을 추가한다: 날짜, 한 일, 판단과 이유, 검사 결과, 다음에 할 일.
- 코드와 함께 커밋한다(이미 커밋했으면 기록만 커밋한다). 커밋 메시지는 한국어로 쓴다. `--amend`는 쓰지 않는다.
- 고쳐도 통과하지 않는 상태가 세 번 반복되면: `git restore --staged --worktree -- <이번 바퀴에 바꾼 코드 파일들>`로 되돌린다. `피드백.md`·`기획서.md`나 `.` 전체를 restore 하지 않는다. 새로 만든 파일은 그대로 두면 실행기가 치워 둔다. 그리고 `진행기록.md`만 `git add`해서 막힌 이유와 다음에 시도할 방법을 적어 커밋한다.

커밋했으면 추가 작업 없이 짧은 요약 한 줄을 출력하고 종료한다. `git push`는 하지 않는다(실행기가 한다).
